# MiloRouter 平台货币与支付设计

2026 年 11 月 24 日 · 设计稿 · 基于生产版本 `0.2.24-ds.3`

## 平台币种的含义

**管理员在全站选择 USD 或 CNY。新订单、余额展示、模型标价、套餐页面和充值设置都使用当前站点币种。用户在充值页只选金额和支付方式。** 原订单的支付凭证继续按交易发生时的币种和金额展示。链上付款时仍要展示用户实际需要转出的 USDT。

平台维持一套整数积分钱包，`100,000,000 credits = 1 USD 等值额度`。模型供应商成本和模型价格以现有计价基准运算，API、工作台和 MiloCode 等入口按同一套计费规则扣积分，API Key 配额、套餐使用额度、兑换码和后台余额调整都以同一账本口径处理。人民币模式在输入和展示时转换。切换币种本身无需产生任何余额流水。

| 金额 | 决定它的地方 | 例子 |
| --- | --- | --- |
| 平台订单价 | 当前平台币种与本站报价 | ¥20.25 |
| 渠道应付 | 渠道支持的法币、订单金额和明确列出的手续费 | 微信支付收 ¥20.25 |
| 实际链上付款 | BEpusdt 创建订单时返回的精确应付额 | 某一订单应转 3 USDT（BEP20） |
| 站内到账 | 报价锁定的基础积分和赠送积分 | 300,000,000 credits |
| 钱包和用量展示 | 当前平台币种与平台基础汇率 | 同一额度显示为 $3.00 或 ¥20.25 |

生产已启用积分账本，当前平台显示 USD，配置为 $1 = ¥6.75。只开放 USDT（BEP20），易支付实例停用，目前没有已配置的付费套餐。订单 #8 实付 3 USDT，账本增加了 300,000,000 credits。现有两套充值逻辑的差异是主要风险。USDT 已按币种报价，微信和支付宝仍按旧「余额充值倍率」计算，在生产倍率为 1 时，开通后 ¥10 会生成 $10 等值额度。商品名的 `CNY` 是写死的占位和示例，用户下单币种由报价决定。 [账本与汇率](../../../backend/internal/service/billing_currency.go) · [下单分支](../../../backend/internal/service/payment_order.go) · [支付设置](../../../frontend/src/views/admin/SettingsView.vue)

## 定价、汇率与精度

平台维护一条基础汇率 `1 USD = X CNY`，使用当前值 6.75 作为首个新规则版本。普通充值、套餐币种换算和余额展示从这里读取。后台变更要显示生效时间、版本和影响预览。只切 USD/CNY 和修改汇率是两个明确的操作。修改汇率会改变当前人民币等值显示和之后的新报价，已经发生的订单、入账和模型扣费按各自记录查询。

首版采用等值充值。基础额度按「用户实付本金折算成美元等值 × 100,000,000」计算，按十进制四舍五入到整数积分。手续费增加应付金额，赠送只增加到账额度。折扣活动按现有业务语义，以较低实付价购买原面额的额度，折扣覆盖的额度单列为活动发放。订单分别记录原面额、折扣后实付本金、手续费、实付本金对应的积分与活动发放积分。当前生产费率为 0，也没有配置充值赠送。

| 首版例子 | 站内报价 | 基础到账 |
| --- | ---: | ---: |
| USD 模式充值 | $3.00 | 300,000,000 credits |
| CNY 模式充值 | ¥20.25 | 300,000,000 credits |
| CNY 模式充值 | ¥10.00 | 148,148,148 credits，当前人民币界面显示 ¥10.00 |
| USD 模式使用 $3 等值余额，平台切到 CNY | 当前余额显示 ¥20.25 | 对应原来的 300,000,000 credits |

现有设计区分用于展示的 `usd_to_cny` 和用于购买余额的 `recharge_rates`，两者有独立的商业含义。当前生产两项等价，首版把常规售价和展示对齐，促销通过折扣、赠送和手续费配置。现有独立字段保留给兼容旧订单和回退。若今后需要设置一个长期独立售价，应把「用户花多少」「到多少额度」明确展示，再单独改变定价规则。BEpusdt 从法币换算 USDT 的报价由网关提供，按其精确返回值冻结。 [原积分账本设计](../add-cny-credit-billing/design.md) · [现有 USDT 报价](../../../backend/internal/service/payment_recharge_quote.go)

法币价按整数分记录，积分按整数记录，汇率运算使用十进制，USDT 金额用十进制字符串或链上原子单位精确保存。API 对超过 JavaScript 安全整数范围的字段使用字符串。输入超过币种精度时明确报错。后台金额统一显示当前平台币种，编辑时保留底层精度。比如目前最低充值为 ¥1 的等值，美元模式下可输的最低美分金额是 $0.15，人民币模式仍是 ¥1.00。最低额向上取整，最高额向下取整。

## 用户充值与渠道选择

| 支付方式 | 平台 USD | 平台 CNY |
| --- | --- | --- |
| USDT（BEP20） | 订单按 USD 报价，BEpusdt 请求使用 `fiat=USD` | 订单按 CNY 报价，BEpusdt 请求使用 `fiat=CNY` |
| 现有微信、支付宝、易支付人民币配置 | 用户页隐藏，后台显示「仅支持 CNY」 | 商户配置完整且启用后显示，按 CNY 收款 |
| 未来配置的其他法币渠道 | 实例支持 USD 才显示 | 实例支持 CNY 才显示 |

首版采用同币种收款策略。以后如果业务上需要让美元站也支持人民币微信或支付宝，可以新增跨币种收款策略。届时用户确认前须看见「实际支付 ¥X，预计到账 $Y」，并锁定换算汇率、手续费、原收款币种和退款口径。

1. 用户页由服务端返回平台币种和可用渠道，统一显示该币种的快捷金额、自定义金额、限额和到账预览。USDT 的单笔 USD/CNY 单选移除。
2. 选择金额和渠道后，服务端报价返回订单本金、折扣、费用、法币应付、预计到账和报价有效期。法币渠道在确认前展示实际要扣的法币金额。USDT 渠道在生成网关订单并取得精确值后，展示应转 USDT、BEP20 网络、收款地址和截止时间。
3. 收到并确认付款后显示「付款已确认，入账中」。充值成功以钱包入账为准。取消或失败的订单最多显示「预计到账」，记录真实状态。结果页和后台订单详情可查原币种、实付、到账与退款。

## 后台支付设置

| 区域 | 建议配置与反馈 |
| --- | --- |
| 平台币种 | 沿用现有全站币种配置作为唯一入口。支付设置引用当前币种和基础汇率，提供跳转入口。切换预览余额样例、可用渠道、限额、套餐售价及生效范围。 |
| 充值规则 | 最低、最高和每日额度明确单位。推荐平台限额和活动门槛按统一的本金等值保存，以当前币种编辑及展示。所有规则在同一份报价中算完。 |
| 支付渠道 | 设置是否启用、支持的法币、渠道原币种限额、收银台方式、回调和退款能力。密钥仅在管理员配置入口维护。BEpusdt 卡片同时展示「支持 USD/CNY」和「链上 USDT（BEP20）」。 |
| 套餐定价 | 录入带币种的基础售价，预览当前站点币种的售价，按已发布价格销售。套餐权益、期限与 API 用量额度单列。 |
| 商品名称 | 前后缀为可选文字，预览用当前站点币种的金额。金额和币种标签由订单生成。 |
| 旧字段 | 统一报价接管后，把「余额充值倍率」「订阅 CNY 换算汇率」改为兼容字段并退出日常配置。 |

切币种时预览哪些已启用渠道会退出用户页、最低面额如何变化、在售套餐的金额如何变化。启用支付但切换后没有可用渠道时，后台明确显示原因，并给出先配置兼容渠道或明确停用新单的选项。支付状态的变更需同步更新首屏配置与报价服务，旧页面以服务器回传的策略版本为准。

平台充值的最低额、最高额、日额度和活动门槛统一按用户选择的充值面额判断。渠道限额按含手续费的实际应付金额判断，使用该渠道的原币种。日限额启用后，在创建订单时按用户和渠道原子预留，确认付款后转为已用，安全取消或确认失效后释放。后台明确日限额的时区、计算范围和重置时间。

## 套餐与平台用量

套餐是购买使用权益，充值是增加钱包积分。套餐记录显式价格、价格币种、期限及权益。切换平台币种时，后台可以按基础汇率生成等值价格草案，确认后一起发布。比如原价 $10 的套餐在人民币模式下建议发布 ¥67.50。实际下单读取已发布价格，套餐卡片、报价和网关应付用同一结果。以后若需要给两种市场独立定价，可增加明确的 USD/CNY 价目。已购买的套餐按原权益与到期日履行。

当前套餐的币种字段主要用于展示，后端处理订单还依赖独立的 CNY 换算选项。生产暂无付费套餐，适合在首次上架前建立明确语义。兼容其他环境已有套餐时，用配置和实际成交记录核准价格及原币种，对无证据的记录标记待核对。USDT 用于购买套餐需要单独接通并验收权益发放。

钱包、兑换、用量、续期、分组订阅额度和工作台消费沿用积分底层。管理员以当前站点币种输入金额时，保存时明确它的单位，换算后写入原有积分或 USD 等值字段。历史用量明细可用当时的扣款和版本显示，趋势图若按当前汇率折算要明确标注口径。 [套餐字段](../../../backend/ent/schema/subscription_plan.go) · [下单实现](../../../backend/internal/service/payment_order.go) · [积分计费审计](../../../docs/SYNC_V0_2_23_BILLING_AUDIT.md)

## 报价、订单及对账

```mermaid
flowchart LR
    UI["当前站点币种和可用渠道"] --> Q["服务端报价"]
    Q --> O["按报价创建订单并保存快照"]
    O --> P["渠道下单和支付确认"]
    P --> L["钱包入账或发放套餐权益"]
    L --> R["结果页、订单记录和对账"]
```

- **报价。** 保存用户、金额或套餐、币种、渠道、应付各项、积分、策略版本及有效期。首次创建订单时提交报价标识和请求幂等键，由服务端校验。若切币种或改价发生在创建前，旧页面上的 $10 需要重新报价。已经创建过的同一请求应返回原订单。
- **订单。** 冻结报价、订单币种和金额、渠道实例、渠道实付币种及应付、积分和费用。网关创建成功后保存其订单号、到期时间以及精确 USDT 应付。遇到调用超时时，按原商户订单号查询和恢复，确认未创建后再重试。已经生成的订单按原条件付款和回调，支付开关或币种变更后仍可查询和结算。旧客户端在启用新策略后提交无币种、无报价的请求时，引导刷新。
- **支付确认。** 核对商户订单、原渠道实例、币种、法币金额及必要的链上金额，充值入账和套餐履约各自按订单幂等。回调重试、用户主动查单及后台任务可以并发，但只产生一笔到账。链上可获得事件标识时记录链 ID、交易哈希及转账事件序号，防止同笔转账被重复核销。少付、多付、超期付款和渠道状态不确定进入异常核对。
- **事实与报表。** 原订单面额按 USD/CNY 分组，渠道实收按收款资产分别汇总，站内发放按钱包流水核对。比如 #8 同时有 $3 订单面额、实收 3 USDT、发放 300,000,000 credits。若做统一营收折算，要标明折算口径和日期。旧订单保留原有凭证，缺失的链上字段显示无记录。历史到账优先使用当时的金额快照，快照缺失时显示实际积分，附带的当前币种金额明确标注为折算值。

充值可复用现有支付订单和 `billing_ledger`，为新订单增加正式报价和退款记录。兼容期保留旧订单字段及读路径。存在重复回调或写库失败时，以渠道查询和账本唯一引用对账。 [当前入账实现](../../../backend/internal/service/redeem_service.go) · [订单快照](../../../backend/internal/service/payment_order_provider_snapshot.go) · [支付统计](../../../backend/internal/service/payment_stats.go)

## 退款

把「原路退多少钱」和「收回多少站内额度」放在同一退款单上，分别用原收款币种和整数积分记录。交易手续费、额外赠送和已消费额度影响退款规则，确认页需要逐项写明。计划先支持全额退款，部分退款在核准手续费、赠送、推荐返利规则后再增加，届时必须限制累计原币退款和累计可冲减额度。

- **支持原路退款的渠道。** 按原订单实收和渠道能力计算，优先冻结可回收额度。提交后根据渠道结果更新，成功后写入一次积分冲减，明确失败则释放，未知或处理中保留冻结并查单。余额不足或套餐权益已使用进入人工核对。退款金额和额度计算使用订单快照。
- **BEpusdt。** 订单详情标注「此渠道不支持自动退款」，隐藏通用退款操作。若要提供人工链上退款，先登记原单、核验退款地址和可回收额度，再提交链上转账。确认实际转出后登记交易哈希并冲减对应积分，交由对账确认。网关收款、人工退款和站内额度调整分别留记录。

当前 #8 的通用「退款」按钮属于显示条件问题，生产渠道已经关闭自动退款。现有退款流程和 BEpusdt 的实际能力见实现。 [退款服务](../../../backend/internal/service/payment_refund.go) · [BEpusdt 适配器](../../../backend/internal/payment/provider/bepusdt.go)

## 实施顺序与验收

| 顺序 | 交付 |
| --- | --- |
| 1. 统一充值 | 以现有积分账本和 6.75 汇率初始化新策略，使所有充值走同一服务端报价。USDT 移除单笔币种选择，修正后台预览、渠道兼容性、到账状态和退款入口。先保持生产的 USD 与 USDT 渠道组合。 |
| 2. 接入人民币渠道与套餐 | CNY 模式下完成真实小额渠道联调，核对实扣和到账。再启用微信或支付宝。套餐上线前确认原始价格和两种模式的标价及权益。 |
| 3. 完善退款与对账 | 按渠道验证可退能力、原币退款和积分冲减。提供异常单、实收及财务核对。 |

验收使用开发库数据和小额订单，切换前后核对订单、网关和账本。

- USD 模式的充值输入只出现 USD，CNY 模式只出现 CNY。用 $3 和 ¥20.25 分别下单，无费用和赠送时均到账 300,000,000 credits。¥10 到账 148,148,148 credits。
- 人民币渠道在 USD 模式下用户页不可选，直接调用创建订单也受到同一规则约束。CNY 模式下实际扣款和预览一致，历史订单仍按原币种展现。
- 浏览器保留旧报价后切币种或修改汇率，提交触发重新报价。已经打开的旧收银台仍可按原订单付款。重复下单、回调与查单并发时核对网关订单和钱包流水各记一次。
- 币种切换后，账户余额、已有 API Key 配额以及套餐额度保有原有积分。核对现有 #8 的 $3 面额、3 USDT 实收和 300,000,000 credits 流水。取消的测试单没有钱包到账。
- 小额订单分别核对网关实收、付款确认、结果页和后台订单信息。对限额边界、USDT 金额小数、失效订单、退款失败和余额不足覆盖验收。

切换前核对未结订单、渠道状态、订单与入账总数，发布后保留新旧订单读取及回调能力。回退优先关闭新报价入口并保留结算能力。已产生新格式订单后，需要确认回退版本支持这些订单的查单和回调，再决定是否回退应用。
